## 1. ledger 前 285 筆

修改前，`test_r02_archive_remains_intact_and_reports_exact_current_source_drift` 用 `mode=ro&immutable=1` 讀總筆數。這個連線不看 WAL，總數停在 285。verifier 用 `mode=ro`，看得到 WAL 裡的 286–303，總數是 303。斷言因此變成 `303 == 285`。

修改後，測試與 verifier 一樣用 `mode=ro` 加 `PRAGMA query_only=ON` 讀總數，所以兩邊必須相同，總數可以繼續增加。另外把 sequence 1..285 做成滾動 SHA-256，WAL 視圖與 immutable 主檔視圖都必須等於：

`d7b084c3daf5630b465946dfa834172125daee33f4fb7baea4574f2582700992`

沒有既有的 hash 欄位。演算法是資料表欄位順序、sequence 必須剛好是 1..285、每一列 `json.dumps(list(row), ensure_ascii=False, separators=(",", ":"))` 再往前接上一個 digest。往後追加不會改這條鏈。改寫前 285 列的任何一列會改 digest，缺號或重排會失敗。verifier 裡凍結的 183 基線與它的 mismatch 錯誤沒有改，測試仍要求那些 drift 錯誤。

這比「總數永遠等於 285」更嚴在歷史本身，只放寬 285 之後的追加。計畫要求的就是這件事。

檔案在工作樹內時，`tests/test_week4_repair_integrity.py` 8 passed。權威庫 SHA-256 前後都是 `2f70e846d4ecb4109f54314e210fb4ba7ce90adc57c420fe6c4f31e8cd7fb366`。沒有 checkpoint。

## 4. getpass 與 pty

修改前，`approve_m2a03_spatial_inputs.py` 呼叫 `getpass.getpass`。它會開 `/dev/tty`，忽略 stdin 上的金鑰，所以測試在有控制終端機時會停住。只把 pytest 脫離 tty 不能當修正。

修改後，stdin 不是終端機時從 stdin 讀一行；stdin 是終端機時仍用 getpass。`main(..., password_prompt=)` 與 `_request_decision_key(password_prompt)` 可以注入提示函式。金鑰仍交給 `verify_decision_key_strict`，沒有新增會把金鑰放上命令列的參數。沒有讀 Keychain，沒有跑 live spatial-r01 批准。

新鮮結果：piped prompt 不呼叫 getpass；tty 仍呼叫 getpass；子程序持有 `/dev/tty` 且 stdin 是 pipe 時，10 秒內回傳 pipe 上的測試鍵。`test_historical_replay_cli_accepts_a_fixture_and_refuses_the_unmarked_path` 與 `test_cli_r03_approval_rejects_tamper_without_publishing` 通過。
