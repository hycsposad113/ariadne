# Ariadne 判讀 skill（J-SITE／J-COMPARE／J-CLIMATE）v1

撰寫：Claude Opus 5.5（Commander），2026-10-17。依據 Founder 10-17 決定：判讀品質不能隨模型浮動，每階段呼叫專屬 skill；複雜 skill 由前沿模型撰寫。

## 為什麼要 skill，而不是直接問模型

同一份資料，直接問模型會得到「把資料換句話說」的回答（10-17 Live 測試：Ariadne 把「未分類餘地 138,892 m²」改寫成「設計機會」，沒有判斷）。skill 把**判斷的方法**固定下來：

1. **輸入組裝固定**：只餵已持久化的確定性結果（證據卡、指標、模擬結果、限制說明），每個值都帶 `metric_id`／`evidence_card` id 與單位。模型不讀檔、不上網、不計算。
2. **判斷框架固定**：每個 skill 有 4–6 個「鏡頭」（lens），每個鏡頭有必答問題與判斷規則。模型必須逐鏡頭思考，再收斂成一個立場。
3. **知識背景固定**：每個 skill 列出必讀知識單元（`knowledge/v2` 的 KU），組裝時把 KU 的 `summary_zh`、`design_implications_zh`、`not_applicable_when_zh` 一起附上。推理段落只准引用這份清單內的 KU。
4. **輸出格式固定**：`judgement-card.schema.json`；觀察 3–8 條、立場一句、推理 2–6 段、信心、修正方向 1–4 項、反例、限制、要問設計者的問題。
5. **驗證固定**（確定性程式，不靠模型自律）：
   - 文字中每個數字都必須等於輸入某個值（容許四捨五入到輸入的顯示精度），否則拒絕。
   - `refs` 與 `knowledge_refs` 必須在白名單內。
   - 禁止詞（見下）出現即拒絕；否定句也算（安全檢查是子字串比對）。
   - 必須有 `counterpoints`；`stance` 為 SUPPORT 時仍必須至少一條 `revision_directions` 或標 `analysis_needed`。
6. **一致性評測**：每個 skill 附固定評測輸入；同一輸入以兩個不同模型各跑一次，比對 stance、主要修正方向的 parameter_family 與引用的關鍵指標是否一致；不一致的項目回頭修 skill，而不是挑比較好的那次。

## 共同的判斷原則（三個 skill 都適用）

- **要有立場**：不能只列優缺點。headline 必須是一句可以被反駁的判斷（例如「我認為港埠方案的街道冬季日照是需要在下一輪修正的實質弱點，而不是可接受的代價」）。
- **條件式判斷優先於排名**：用「若設計目標偏重 X，則…；若偏重 Y，則…」表達取捨；不宣告總冠軍。
- **分清三種東西**：確定性結果（數值）、目標差距（數值 vs 基準）、設計判斷（解讀）。只有第三種是 Ariadne 的意見，要寫成意見。
- **方法限制要進入判斷**：例如 E5 是粗網格篩選、背風區不準 → 不能據此下風安全結論；空間語法是潛力不是實測人流。
- **修正方向要可執行**：寫到「哪裡、改什麼參數族、預期方向、代價」，讓第 3 期的修正提案可以接手。不寫具體新數值（數值由確定性生成器或 Founder 決定）。
- **把設計者放回迴圈**：每張卡最後問 1–3 個只有設計者能回答的問題（偏好、優先順序、在地知識）。

## 禁止事項

- 不計算、不推估新數值、不補零；未知寫「資料缺口」。
- 不建立或暗示 HumanDecision；不寫「已核准」「批准」「正式接受」「決策成立」。
- 不把空間語法寫成人流、把 UTCI 寫成實測、把 E3 寫成能源認證、把 E5 寫成風安全結論。
- 不宣告總冠軍或「最佳方案」。
- 不引用白名單外的文獻、作者、網址。

## 檔案

- `judgement-card.schema.json`：輸出格式。
- `J-SITE-zh.md`、`J-COMPARE-zh.md`、`J-CLIMATE-zh.md`：三個 skill 的框架、輸入、必讀 KU、驗證規則。
- `eval/`：一致性評測輸入與預期（第 2 期施工時建立）。
